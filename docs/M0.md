## 1. Locked product scope

Deliver one responsive, role-based web application using Next.js App Router, TypeScript, Tailwind CSS, Prisma, and one PostgreSQL database. D1–D5 are logical table groups in that database.

| Role | Allowed scope | Explicitly excluded |
|---|---|---|
| HR | Read/write workers and synthetic source records for authenticated user's company | Other companies; P5 reporter identity |
| Worker | Read own contracts, versions, deductions and company-period reconciliation status; submit own P1 feedback and P5 category report | Other workers; auditor scores; raw P5 records |
| Auditor | Read company-level ranked assessments, coverage, explanations and redacted evidence summaries | Worker-level records, raw feedback, payslips, report identity/text |
| Demo operator | Protected demo reset/recalculate actions only | Any implied production administration or public reset access |

Authorization is enforced server-side on every route and scoped query. UI role choice is never authorization. No public self-registration. All identities and records are synthetic. Application routes stay within the single app: `/login`, `/hr`, `/hr/workers/[id]`, `/worker`, `/worker/contract`, `/worker/contributions`, `/worker/report`, `/auditor`, and `/auditor/companies/[id]`.

Proposed API contract, matching `SPEC.md` §8.3:

| Endpoint | Required server scope |
|---|---|
| `POST /api/demo/session` | Demo-only seeded identity; establish server-side session |
| `GET /api/hr/workers` | HR; authenticated company only |
| `POST /api/hr/workers/:id/contracts` | HR; worker must belong to authenticated company |
| `POST /api/hr/attendance/import`, `/api/hr/payroll/import`, `/api/hr/deductions/import` | HR; all rows scoped to authenticated company and validated before write |
| `GET /api/worker/contract`, `POST /api/worker/contract-feedback`, `GET /api/worker/contributions`, `POST /api/worker/reports` | Worker; authenticated worker only; report route must not log identity-bearing request details |
| `GET /api/auditor/companies`, `GET /api/auditor/companies/:id/risk` | Auditor; redacted company-level DTOs only |
| `POST /api/demo/recalculate`, `POST /api/demo/reset` | Seeded demo operator only; reset disabled outside approved demo environment |

Suggested immutable policy identifier: `ruleVersion = "demo-v1"`. This is a demo policy label, not a regulatory version.

P0 includes F01–F12 and AC01–AC14 as specified. Out of scope: real BPJS/HRIS/payroll integrations, ML/LLM scoring, payment processing, real identity or health data, legal classification, automatic fraud verdicts/sanctions, microservices, and features explicitly deferred until after P0.

## 2. P1–P5 data contract

All periods use `YYYY-MM`; all IDR money uses non-negative integer rupiah (no floating point). Source records and mock confirmations are visibly marked `Synthetic / Demo`.

| Process/store | Accepted inputs | Persisted output | Required behavior |
|---|---|---|---|
| P1 / D1 | HR contract content and effective dates; worker-linked feedback on a specific version | Immutable `ContractVersion` rows; restricted `ContractFeedback` rows | Publish creates monotonically increasing version; reject overlapping effective periods; period lookup uses effective dates. Feedback is a reported concern, not a legal finding, and is separate from P5. |
| P2 / D2 | Worker-period attendance and payroll components | Attendance/payroll source rows and period evaluation | Compare against contract effective in the payroll period. Evaluate fixed-component differences and recurring identical variable allowance over three consecutive periods with stable attendance. Signals require explanation and are not proof of under-reporting. |
| P3 / D3 | Worker 1% deductions; company-period mock BPJS confirmation with explicitly labeled employee-share amount | Source provenance and company-period reconciliation result | Compare same company, period, and employee-share basis only. Never compare 1% deductions directly to a 5% total. Emit `MATCHED`, `MISMATCH`, `PENDING`, or `UNVERIFIED` per policy below. |
| P4 / D5 | P1/P2/P3 evaluation plus P5 company-period count adapter | Append-only assessment snapshot and its indicators | Weights 25/30/35/10; once per category/company/period. Persist rule version, explanations, coverage, source period and assessment time. Preserve prior snapshots. |
| P5 / D4 | Authorized worker's selected category and period; company resolved transiently from session | Random report ID, company, period, category, timestamp | Persist no reporter/user/worker ID, contact, IP, session ID, free text, attachments, or identity-bearing request data. Auditor/P4 receive only company-period counts once threshold is reached. |

### Evidence indicator contract

| Indicator | Trigger | Weighted category / contribution |
|---|---|---|
| `P1_WORKER_STATUS_DISPUTE` | At least one linked worker feedback explicitly says reported work arrangement differs from contract classification | `STATUS_FEEDBACK_DISPUTE` / 25 |
| `P1_RAPID_STATUS_VERSION_CHANGES` | At least two classification changes across a three-month history | Informational only in P0 / 0 |
| `P2_FIXED_COMPONENT_CONTRACT_DIFFERENCE` | Reported fixed wage or fixed allowance differs from period-effective contract | `WAGE_COMPONENT_INCONSISTENCY` / 30 |
| `P2_RECURRING_VARIABLE_COMPONENT` | Same declared variable allowance in three consecutive periods with stable attendance | `WAGE_COMPONENT_INCONSISTENCY` / 30; category weight counted once even if both P2 indicators trigger |
| `P3_CONFIRMED_EMPLOYEE_SHARE_DELTA` | Comparable confirmed employee-share amount differs from deduction aggregate beyond tolerance | `CONTRIBUTION_DELTA` / 35 |
| `P5_REPORT_COUNT_THRESHOLD` | At least three protected reports for company in the same configured reporting window | `REPORT_CLUSTER` / 10 |

Coverage is `COMPLETE` only when P1, P2, and P3 evidence is sufficient for the assessed period; otherwise `INCOMPLETE`. With incomplete coverage, expose observed score as provisional and label risk `INSUFFICIENT_DATA`. With complete coverage, labels are `LOW` 0–19, `MEDIUM` 20–49, `HIGH` 50–100. Incomplete companies appear in a separate evidence-completion queue. P5 is operational with zero reports; counts below 3 are not exposed or scored.

## 3. Status and arithmetic policy

### P3

Let `deductionSum` be the sum of the company's worker 1% deductions for a period, and `confirmedEmployeeShareAmount` be the mock BPJS confirmation for that same company-period and same component. Use:

The mathematical tolerance is `max(IDR 1,000, 1% of deductionSum)`. Compare without floating point: a delta is within tolerance iff `abs(delta) <= 1,000` **or** `abs(delta) * 100 <= deductionSum`. Use safe integer bounds or `BigInt` for multiplication.

All calculations use integer-safe arithmetic. Store a signed `delta = confirmedEmployeeShareAmount - deductionSum` only when a comparable confirmation exists.

| Status | Exact condition | Delta |
|---|---|---|
| `MATCHED` | Comparable confirmed amount exists and `abs(delta) <= tolerance` | Present |
| `MISMATCH` | Comparable confirmed amount exists and `abs(delta) > tolerance` | Present |
| `PENDING` | Confirmation is not yet expected according to fixture-configured due date/window | Absent |
| `UNVERIFIED` | Confirmation is missing after expected window, basis is non-comparable, or evidence is otherwise insufficient | Absent |

`MISMATCH` means a data discrepancy requiring review, not proof of misuse. Worker-facing status is always described as **company-period reconciliation**, never proof that an individual's contribution settled. Mock confirmations are labeled `Sumber: Simulasi BPJS`.

### P2 and P4

Contract lookup for period `YYYY-MM` uses the version effective during that period, not latest version. Fixed amounts compare as integer IDR. Recurring variable allowance is a review signal only. P4 sums each triggered category once; rapid P1 status changes add no points. Missing inputs never count as a clean finding.

## 4. Seed and golden fixtures

Seed exactly 5 fictional companies and 100 fictional workers (20 per company) for deterministic baseline. Seeded demo users cover HR for each company, at least one worker per company, an auditor, and the separately authorized demo operator. IDs and credentials are synthetic and must not be secrets committed in the repository. Use a fixed assessment period such as `2026-09` and fixed fixture timestamps so tests and rehearsals are reproducible.

For every complete golden case, P1, P2 and P3 are evaluated with sufficient records; clean/non-triggered processes have explicit source evidence rather than inferred zeroes.

| Company | Seeded evidence | Expected P1/P2/P3/P5 | Expected P4 |
|---|---|---|---|
| A — Gabungan | One qualifying linked status feedback; deduction sum IDR 100,000; comparable confirmed employee-share IDR 90,000; P2 sources complete and clear | P1 triggered; P2 evaluated clear; P3 `MISMATCH`, delta -IDR 10,000; P5 below threshold | `25 + 35 = 60`, `HIGH`, `COMPLETE` |
| B — Upah | Period-effective contract: base IDR 5,000,000 and fixed allowance IDR 500,000; payroll reports same base and fixed allowance IDR 650,000; attendance present; P1/P3 evaluated clear | `P2_FIXED_COMPONENT_CONTRACT_DIFFERENCE` triggered; other weighted categories clear | `30`, `MEDIUM`, `COMPLETE` |
| C — Bukti Belum Lengkap | P1/P2 sufficient and clear; deduction sum IDR 80,000; no confirmation after configured expected window | P3 `UNVERIFIED`, no numeric delta | Provisional observed score `0`, `INSUFFICIENT_DATA`, `INCOMPLETE`; never `MISMATCH` or `LOW` |
| D — Kontrol Bersih | Sufficient P1/P2/P3 inputs; comparable P3 amounts within tolerance; no qualifying feedback or wage signals | All weighted rules clear; P3 `MATCHED` | `0`, `LOW`, `COMPLETE` |
| E — Laporan Terlindungi | P1/P2/P3 complete and clear; exactly three protected reports in configured company-period window; no reporter identifiers persisted | P5 threshold triggered | `10`, `LOW`, `COMPLETE`; auditor sees eligible aggregate, never reporter details |

Additional deterministic regression vectors:

- P3 equal deductions/confirmation → `MATCHED`; within tolerance → `MATCHED`; beyond tolerance → `MISMATCH`; before configured due date with no confirmation → `PENDING`; after due date with missing/non-comparable confirmation → `UNVERIFIED`.
- Company E variant with one or two reports → zero P5 contribution and no displayed numeric report count.
- P1 history with two classification changes across three months → `P1_RAPID_STATUS_VERSION_CHANGES` informational, zero P1 score by itself.
- Three consecutive same variable-allowance values with identical monthly actual/overtime hours → `P2_RECURRING_VARIABLE_COMPONENT`; P2 category contributes 30 at most once, including when fixed-component indicator also triggers.
- Publishing v2 leaves v1 contents unchanged; a historical payroll period continues selecting its effective contract version.
- Recalculation after an input change appends an assessment snapshot and preserves the previous snapshot.
- Cross-company HR IDs, cross-worker requests, auditor raw-worker access, and unauthorized demo reset/recalculate are denied server-side.
- P5 persistence/API inspection confirms no reporter identity fields; aggregation under threshold is suppressed.

## 5. Demo sequence and copy

1. Auditor opens ranked company overview; explain score, triggered rules, coverage and synthetic-data label.
2. HR publishes a new contract version; show previous version remains readable.
3. Show period-specific payroll/attendance evidence and a wage signal.
4. Show same-basis worker-share deduction and mock confirmation comparison; distinguish `UNVERIFIED` from `MISMATCH`.
5. Recalculate; show changed indicator/rank and a new stored assessment timestamp.
6. Worker views own contract/contribution status and submits a categorical report; auditor sees only eligible thresholded aggregation.

Required interpretation copy: **“Indikator risiko dan hasil pencocokan merupakan sinyal awal untuk diverifikasi auditor; bukan pembuktian fraud atau penetapan kewajiban hukum.”** Use `indikasi`, `perlu verifikasi`, `belum dikonfirmasi`; never claim official BPJS verification or individual settlement from a company total.

## 6. Decision options and implementation details

These are implementation choices proposed to make fixtures deterministic. Confirmed choices are recorded in §7:

1. **HR input mode:** seed + validated forms for P0; CSV import UI deferred if time-constrained. Underlying source data remains persistable and recomputable.
2. **P3 due-date behavior:** each fixture provides an explicit confirmation-expected timestamp; `PENDING` before it and `UNVERIFIED` after it if confirmation remains unavailable. This avoids inventing a statutory deadline.
3. **P5 window:** count reports by company and explicit `YYYY-MM` period; threshold is 3 in that window. No smaller count is returned to auditor/P4.
4. **Operator identity:** maintain seeded demo operator capability separately from ordinary HR/Worker/Auditor access; exact sign-in mechanism is to be chosen without granting reset rights to all auditors.
5. **Demo period:** use `2026-09` as deterministic baseline period unless team prefers another period; fixture timestamps must not depend on wall-clock time.
6. **Form-only P0 vs CSV:** if team requires CSV imports for F05, define accepted CSV columns/validation contract before M2; otherwise retain the P0 feature through validated forms and deterministic seeds.
7. **Stable attendance fixture:** define the P2 regression vector as identical `actualHours` and `overtimeHours` across its three months; no production threshold for “stable” is implied.

M0 exit gate is satisfied for the baseline recorded in §7. Do not treat proposed fixture numbers as verified institutional rules.
