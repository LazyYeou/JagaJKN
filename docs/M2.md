# M2 — Evidence Pipeline

**Scope:** P1 contract versions/feedback, P2 attendance/payroll evaluation, and P3 contribution reconciliation. One PostgreSQL database; D1–D3 remain table groups in that database.

## Confirmed implementation decisions

These demo assumptions were confirmed by the user before implementation; they do not claim statutory rules:

1. Closing a contract version writes an append-only `ContractClosure`; it never edits prior contract content. Contract effective dates start on the first day of a month.
2. A payroll period is evaluated only when exactly one contract version covers the entire month. Gaps or mid-month overlap produce insufficient evidence; no proration or arbitrary version choice.
3. Three-month repeated-variable-allowance signal requires a **positive** repeated amount and identical actual/overtime hours across all three months. Rp0 is not a payment signal.
4. P3 due times come from explicit synthetic fixture configuration. No configured deadline means missing confirmation is `UNVERIFIED`.

## Implemented flows

### P1

- `POST /api/hr/workers/:id/contracts` authorizes company scope, validates integer IDR and first-of-month dates, serializes publication, increments version number, and creates the new contract plus prior-version closure in one transaction.
- `GET /api/hr/workers/:id` and `GET /api/worker/contract?period=YYYY-MM` return authorized contract history and effective period version.
- `POST /api/worker/contract-feedback` accepts only a worker-owned contract version and controlled categories. Feedback remains linked and is not exposed in HR/auditor DTOs.
- `evaluateP1StatusFeedback` emits an explicitly reported status-dispute indicator for the contract effective in that period. It makes no legal determination.

### P2

- HR form APIs upsert company-scoped `AttendanceRecord` and `PayrollRecord`; validate the whole batch before writing.
- Every source change and P2 evaluation commits in one serializable transaction.
- `WAGE_COMPONENT_INCONSISTENCY` evidence groups fixed-component differences and the three-month positive repeated-variable pattern. Persisted `WageEvaluation`/`WageIndicator` snapshots include coverage, rule version, observed count, and explanation.
- Missing source or contract data stays `INSUFFICIENT_DATA`; observed signals can be reported provisionally with incomplete coverage.

### P3

- HR deduction form upserts only workers belonging to the authenticated company. Reconciliation compares complete same-company/same-period 1% employee-share deductions with `confirmedEmployeeShareAmount` from the mock BPJS adapter.
- `confirmedTotalAmount` is not a direct comparison basis. Worker API labels results as company-period status, not individual payment proof.
- `MATCHED`, `MISMATCH`, `PENDING`, `UNVERIFIED` follow the documented integer tolerance. Missing/non-comparable evidence never produces a delta.
- Every recalculation appends `ReconciliationResult`, including count/sum provenance, basis, mock confirmation reference, due time and evaluation timestamp. Snapshot timestamps are monotonic per company-period so latest reads remain unambiguous.
- `npm run db:recompute-evidence` appends evaluations for existing source periods without resetting or rewriting source records.

## Schema and data preservation

Migration `20261010000000_m2_evidence` adds append-only contract closures, persisted P2 evaluations, and P3 provenance/history. It backfills closure records from M1 `effectiveTo` values and links prior reconciliation snapshots to available deposit confirmations. It does not delete or rewrite M1 contract/evaluation values.

Seed now runs P2/P3 services over the synthetic M0 fixtures; it produces five P2 snapshots and six P3 statuses across the golden period plus pending control.

## Verification

- Unit: effective contract selection, full-month coverage, P1 self-reported dispute, P2 fixed/recurring rules, positive-only variable pattern, P3 statuses/tolerance/no fabricated delta.
- Database integration: repeatable seed; A/B/C/D/E baseline outputs; P1 immutable publication/closure; P2 result changes and history; P3 result changes and history; role/tenant scoping.
- API integration: session-derived scope, invalid/forged roles, cross-company IDs, worker feedback ownership, source imports, worker contribution labels, operator-only reset.
- Migration backfill integration: apply M1 schema+synthetic rows, apply M2 migration, verify contract closure and P3 provenance retained.

Local `.env` database received the additive M2 migration and reported schema up to date. `npm run db:recompute-evidence` appended 15 P2 and 15 P3 snapshots for 5 companies without resetting source data.

M2 does not include P4 scoring, CSV import, or official BPJS integration; those remain outside this milestone's confirmed scope.
